# Web match helper

The Rust helper handles `competitive16-helper://` browser links, registers a user-level protocol, and runs a small system tray with Open, Settings, Uninstall Helper and Quit. Setup and launch commands detach without leaving a terminal. Windows x64, Linux x64, and Linux ARM64 are supported; installation requires no administrator rights. Windows also registers a per-user Installed apps uninstall entry. Uninstall asks for confirmation and refuses while a helper match or task is active. It removes helper executables, updates and the URL handler, while keeping game files, native recovery data and saved settings. `config.cfg` is strictly out of bounds.

CS 1.6 uses the same game adapter, React scoreboard, crosshair profiles, animated kill cards, native pings, asset pipeline, scanner supervision and recovery code as the desktop client. The helper downloads a signed background runtime once and caches it. The runtime has a separate bootstrap entry: it creates no launcher window, restores no desktop account, and persists no browser session token. It runs only for checks, setup, asset synchronization or the managed game, then exits after cleanup. CS 1.3 keeps its separate legacy launch adapter.

CS 1.3 selection requires `hl.exe` (or native Linux `hl_linux`) plus a `cstrike` or `cstrk13` mod containing `liblist.gam` and its client library. Version metadata must identify 1.3. The Windows AGC build with stale version `1.1` is accepted only with the same exact 655360-byte client DLL SHA-256 used by the desktop adapter, including under Wine; this is compatibility evidence, not authenticity or protocol approval. A folder containing only the Half-Life `valve` mod is incomplete, and a 1.6 installation cannot be selected as 1.3. The helper never installs or repairs missing game files. Windows folder selection uses an activated topmost owner; Linux uses the existing Zenity picker.

Both 1.3 and 1.6 manual folder pickers first validate the selected folder, then search its descendants for an installation of the requested version. Hidden directories are included. Search is read-only, breadth-first, limited to eight levels, 512 directories and 4096 entries, with a five-second budget checked between filesystem operations. Links/junctions are skipped; inaccessible directories are skipped. Direct selection wins, then the first matching folder in sorted breadth-first order. Only the resolved game root is saved; saved paths and launches continue to use direct validation, without repeating recursive discovery. Desktop pickers use the same search limits. CS 1.6 requires 1.6 metadata when `liblist.gam` is present; the desktop's existing missing-metadata standalone checks remain available.

Runtime archives are signed with the pinned Ed25519 key and the distinct `16competitive.helper-runtime.v1` context. Every invocation verifies the signed manifest and all cached runtime files. Archive extraction rejects traversal, links, unexpected files and mismatched sizes/hashes. Older signed versions cannot roll back an installed runtime. The helper checks for updates before resuming the original launch parameters; interrupted downloads never replace a verified runtime.

The browser checks the helper at login and on Play. Competitive modes require the runtime's verified native device check and a valid selected installation. Launch rechecks device status, authenticates the browser's current account in memory, fetches its own active match credentials, verifies required assets and runs the existing managed game lifecycle. Backend rules remain authoritative. Native release approval, short-lived leases, fixed two-hour tickets, server endpoint gates, DLL journals and independent crash recovery remain in force.

The runtime control channel is authenticated loopback TCP, including on Windows GUI processes where stdin is unavailable. Account and match credentials are never placed in process arguments. The separate browser settings bridge requires an exact allowed Origin plus a random capability; it exposes only typed settings/setup actions. Native push-to-talk transitions use a bounded, authenticated event stream and expire closed if their heartbeat stops. No renderer receives filesystem or shell access.

Startup and one-shot runtime replies have a five-minute read timeout. After a successful game-launch or microphone-ready event, the control channel stays open through quiet sessions until the runtime closes it. The runtime retains its fixed two-hour session limit and normal shutdown/recovery behavior.

One Discord connection lives in the Rust tray. Browser activity leases expire after 90 seconds, and a managed game renews its own lease even after the browser closes. Discord joins go through the existing authenticated party endpoint. No browser account token is stored by the tray. Tray upgrades retire only older installed tray instances; game workers and recovery remain independent.

Both `npm run release:local` and the Actions release package and sign Windows/Linux support runtimes alongside the native helper. The public web build fingerprints the Rust sources, shared launch contracts and native release pin. Launcher package metadata is excluded, so launcher-only version bumps remain compatible with reused helper binaries. Changes to fingerprint inputs require rebuilding the helper and web app together. Development-only runtime overrides are excluded from release behavior.

Validation includes Rust security/lifecycle tests, shared game integration regression tests, native Discord IPC tests, archive signing tests and `scripts/native-helper-runtime.test.mjs`. The latter can run in an interactive Windows VM against a local fixture API and an owner-provided game installation, checking real launch, existing HUD frames, device/origin gates and restoration of original DLL hashes. Test fixtures never copy or inspect player configuration files.

Failed companion-runtime actions retain a bounded `runtime-error.json` in the helper configuration directory with only the time, action stage, and an allowlisted system error code. It never contains account tokens, connection credentials, server addresses, or raw error messages. The native error dialog includes the stage/code for diagnosis.

Web voice uses the connected helper runtime for microphone capture, delivering an audio-only local WebRTC stream to the browser through an Origin- and capability-checked loopback offer. Capture is sandboxed, limited to audio, and stops after disconnect or the fixed two-hour session lifetime. Players without a connected helper keep browser microphone capture and the normal browser permission prompt. Microphone access remains subject to OS privacy settings.

Submitted web issue reports request bounded, redacted game console tails and saved match launch context from the helper through the existing authenticated bridge. Diagnostics are collected only when reporting. A separate diagnostics runtime cannot recover the game process’s in-memory FPS samples; those are explicitly unavailable. If the helper cannot be reached, the report still submits browser logs with the missing helper diagnostics marked.
